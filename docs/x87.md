# x87 probe results (M0-07)

## Current evidence correction: operand encoding in both probe encoders

The historical Unicorn and Rosetta runners discarded the sign when encoding a
corpus operand whose `exp` was `"zero"`. Their reported `−0 → +0` behavior was
therefore a harness defect, not evidence about either execution engine. The
signed-zero explanations and associated historical totals below are superseded
by this correction; the historical captures are retained for diagnosis.

The C (Rosetta) encoder had a second defect with the same shape: `put80` had
no branch for `kind == 3` (NaN), so every NaN corpus operand fell through to
the numeric path and was encoded as exponent `0x3FFF` — the finite value
1.5·2^(exp−16383) — instead of a NaN. All 2,855 NaN operand images in the
corpus were affected. The historical "NaN-class C-bit corners" attributed to
Rosetta in the section below were an artifact of that: with the branch added,
Rosetta reports unordered on every NaN comparison exactly like the SDM.

Both encoders now retain the zero sign bit and encode NaN as NaN.
`re/x87probe/test_operand_encoding.py` checks the Python encoder, compiles and
executes the actual pure-C encoder on the host for ten operand shapes (zeros,
infinities, quiet/signalling NaNs, normals, raw-biased), runs Unicorn `FLD`,
`FST` and `FSQRT` negative-zero witnesses at PC24/53/64, and asserts that the C
and Python encoders emit byte-identical 10-byte images for every shape. The
zero-sign and NaN tests both fail before their corrections and pass after.

A fresh full Unicorn run contains 21,702 rows and no recorded emulator faults;
195 rows change (108 `fdiv`, 36 `fmul`, 36 `fsqrt`, and 5 each `fsin`, `fld`,
`fst`). The unchanged referee reports 17,614 agree / 3,793 mismatch, with other
special buckets; `fld` and `fst` now each agree on all 325 rows. These are
diagnostic counts, not whole-game or bit-exact transcendental acceptance.
`cargo test -p slr-x87 --test probe_trusted` passes against the corrected capture;
its pre-existing approximate-transcendental checks still do not satisfy ADR 0007.

A third leg now exists. Rosetta 2 was installed on this host during this review
(`softwareupdate --install-rosetta --agree-to-license`), and the same probe
source builds as an x86_64 Mach-O binary and runs under it directly — no Wine is
needed, because the probe only uses host x87 inline asm. That leg reports
**20,324 agree / 1,083 mismatch** and, on every non-unnormal arithmetic row,
agrees with SoftFloat bit-for-bit at all three precision controls. See
"Rosetta leg" below for the per-op table.

The frozen corpus, source hashes, previous/current raw Unicorn results,
comparison tables, negative controls and test receipts are under
`re/out/boot/ownership-20261021T021707Z/x87-corrected/` (negative-control receipts
are in its parent). Canonical `re/out/x87/uc_results.jsonl` contains the corrected
capture; the previous file is retained as `uc_results-legacy.jsonl` in that
archive. Neither SoftFloat results nor stock inputs were changed. The
`manifest.json` in that archive predates the canonical file's replacement and
records the legacy hash under the canonical path; `audit-20261021/audit.json`
records both real hashes plus an independent replay whose bytes are identical
to the canonical capture.

Physical x87 confirmation remains open. Rosetta is translated execution, not
Intel microcode or Intel silicon: it corroborates the trusted table and supplies
a PC-sensitive third leg, but ADR 0007's real-x87 paragraph is still unmet and
`docs/x87.md` makes no claim otherwise. Transcendentals stay APPROX. Rosetta is
exact or within 1 ulp on `f2xm1`, `fyl2x` and `fpatan`, but on `fsin`/`fcos` it
is markedly *worse* than Unicorn (up to 1.9e17 ulps from the correctly rounded
value, concentrated on π/2-near and huge arguments), so it cannot pin those two
and no tolerance was changed here.

Ticket: issue #8 (plan id M0-07), reworked on `exact-port` (the historical
`m0-07-x87-probe` branch no longer exists; its tip `f98615f` is an ancestor of
`exact-port`).
Probe suite: `re/x87probe/` (tracked). Regeneration: `re/x87probe/README.md`.
No vectors are committed: the corpus, raw oracle outputs and the referee

## Oracles that actually ran

1. **Berkeley SoftFloat, Release 3e** (`ucb-bar/berkeley-softfloat-3`,
   `8086-SSE` specialize, stock `build/Linux-x86_64-GCC` Makefile driven by
   the system `gcc` = Apple clang 21.0.0 on arm64 macOS). `extF80` add/sub/
   mul/div/sqrt/rem, `extF80_to_i32`, quiet/signaling compares. Tininess
   detection: `softfloat_tininess_beforeRounding` (x87 choice).
2. **Unicorn 2.1.4** (shared venv `~/slr-oracle-venv`). Fresh 32-bit instance
   per vector: FPCW set from the vector's (PC, RC), operands loaded as exact
   80-bit images via `FLD tbyte`, one instruction stub, ST(0)/memory/flags
   read back exactly. Final stub forms (after three fixed harness bugs —
   wrong `FSUB`/`FDIV` direction forms, `FSTP`-instead-of-`FST`,
   `FISTTP`-instead-of-`FISTP m64`, ST1/ST0 misread): `FADD ST0,ST1` D8 C1,
   `FSUBR ST0,ST1` D8 E9 (= a−b), `FMUL ST0,ST1` D8 C9, `FDIVR ST0,ST1`
   D8 F9 (= a/b), `FST m64` DD 15, `FISTP m32` DB 1D / `FISTP m64` DF 3D.
3. **Rosetta 2** (translated execution of an x86_64 Mach-O probe on this arm64
   host; `re/x87probe/rosetta/build.sh`, output `re/out/x87/probe-rosetta`).
   Host x87 inline asm, so it exercises real translated x87 instructions rather
   than an emulator model. Same per-op stubs and load order as the Unicorn leg,
   fresh `FNINIT` + `FLDCW` per row. It honors PC+RC and agrees with SoftFloat
   on all 4,088 non-unnormal arithmetic rows at every precision control.
4. **mpmath 1.4.1 tiebreaker** (transcendentals only, 200-bit precision,
   correctly rounded to 80-bit per RC). Not a ticket oracle; resolves
   Unicorn-vs-SDM questions where SoftFloat has no coverage. Out-of-domain
   inputs (`|x|>1` for `F2XM1`, extreme `FYL2X` magnitudes) are excluded from
   comparison rather than fed to `power()`.

**Precision-control emulation (a finding in itself):** SoftFloat always
rounds the 64-bit significand unless `extF80_roundingPrecision` is set to
32/64. The harness maps PC 24/53/64 to precision 32/64/80 for
`fadd/fsub/fmul/fdiv/fsqrt` only (`"pc_applied": true); every other op runs
at precision 80 (`"pc_applied": false). This matches the SDM exactly: PC
shortens only the significand (low bits zeroed, verified on tie vectors);
the exponent keeps its full 15-bit range. `slr-x87` (M0-14) should copy
this wrapper strategy.

**Referee rules** (`compare.py`): register results compared bit-for-bit
(sign + biased exponent + significand), except NaN payloads are

of 21,702 (plus special/NaN buckets; see `results.json`). The pre-correction
referee reported 17,429 / 3,978 against the same corpus; the difference is the
195 rows the sign-dropping oracle encoder mis-executed.

## Trusted-operation table

Legend per cell: `S` SoftFloat agrees-or-justified, `U` Unicorn agrees,
`R` Rosetta agrees, `s`/`u`/`r` oracle not applicable there by construction
(U ignores PC; S has no transcendentals). Verdict **TRUSTED** means cleared for
bit-exact use in `slr-x87`; **APPROX** means cleared only with a tolerance;
**UNTRUSTED** means do not use.

### Transcendentals (ignore PC+RC per SDM; approximate per SDM)

Unicorn-vs-mpmath (SoftFloat has no transcendentals), fresh referee with the
corrected encoders: fsin 40 agree / 255 mismatch, fcos 73/222, fpatan 28/212,

(0 differing pairs of 6,280); RC-independence verified except one denormal-
input `fsin` anomaly (RC2 returns a mid-range value where other RCs return
0 — untrusted input class, game-irrelevant).

Rosetta-vs-mpmath, measuring significand distance on the rows where both
agree on sign and exponent (200-bit correctly-rounded reference, same
`compare.py::mpmath_ref`):

| op | rows | exact | within the 16,384-ulp contract | max ulp |
|----|------|-------|-------------------------------|---------|
| fsin | 204 | 61 | 74 | 1.9e17 |
| fcos | 223 | 106 | 113 | 1.8e16 |
| fpatan | 240 | 209 | 240 | 1 |
| f2xm1 | 35 | 35 | 35 | 0 |
| fyl2x | 295 | 259 | 295 | 1 |

So Rosetta is **far better** than Unicorn on `fpatan`, `f2xm1` and `fyl2x`
(exact or 1 ulp everywhere) and **far worse** on `fsin`/`fcos`. The large
deviations cluster in two places, both measured on the corpus:

- 80 of the 120 over-contract moderate-argument rows have a result exponent
  below −10, i.e. π/2-near cancellation: Rosetta keeps the leading digits and
  loses the tail. Exemplar id 12744, x = π_f64, RC up: Rosetta `0x8d2fff…`
  against the correctly rounded `0x8d3131…` — a relative error of ~3e-10.
- The other 40 are ordinary-magnitude results, and 120 more over-contract rows
  have |x| ≥ 2^33, where argument reduction dominates.

This is a property of Rosetta's translated `FSIN`/`FCOS`, not of the harness:
a four-line clang `-arch x86_64` program that loads π_f64 and executes `FSIN`
reproduces `0x8d30000000000000` at PC24, PC53 and PC64 alike, while the
correctly rounded image is `0x8d313198a2e03707`. `FSIN`/`FCOS` are also
PC-independent here, as the SDM says they should be.

## Edge-case findings (ticket scope items)

- **Denormals:** ext subnormals and f32/f64 subnormals behave sanely on all
  three legs for arithmetic; pseudo-denormal and unnormal encodings are the
  every-leg-diverges zone (see tables). Game-irrelevant (no producer).
- **Exponent range beyond f32:** full 15-bit register range confirmed on
  both emulator oracles — no f32-range clamping before an explicit `FST m32`
  (vectors at exp 128/1023/1000/10000/16382 all agree at PC64).
- **Double rounding:** eliminated at PC=24 by the significand-rounding
  itself (boundary-pair vectors agree SoftFloat-side at PC24 in every RC);
  Unicorn cannot confirm (ignores PC), but Rosetta does confirm it — it
  returns `0x8000…0000` at PC24 and `0x8000004000…` at PC53/64 for id 0,
  matching SoftFloat exactly.
- **NaN payloads:** the emulator oracles differ in propagation payload;
  comparison is payload-insensitive by design. Rosetta preserves the corpus
  payload exactly on `FLD` (including the signalling `0x8000000000000001`
  image) and reports unordered on every NaN comparison, which is the SDM
  result and the reason the 20 "NaN-class" rows above are the SoftFloat
  harness's parser, not Rosetta's behavior. The game never branches on
  payload bits.
- **FIST P:** Rosetta honors RC on `FISTP` (2.5 → 2,1,2,1 across RC0–3,
  confirming RC1=down, RC2=up, RC3=truncate rather than a silent nearest) and
  returns the x87 indefinite `0x80000000` for i32 overflow while the i64 form
  returns the true value — both match SoftFloat on all 285 rows. The
  `i64`-versus-`i32` split at exp 31 is the intended width difference, not a
  divergence.

## Rosetta leg (third oracle)

Runner: `re/x87probe/rosetta/probe.c`, built by
`re/x87probe/rosetta/build.sh` as an x86_64 Mach-O binary
(`clang -arch x86_64`) and executed directly under Rosetta 2 on this arm64

`run_unicorn.py`, fresh `FNINIT`+`FLDCW(pc,rc)` per row. Referee:
`re/x87probe/compare_rosetta.py` (same NaN-tolerant rules as `compare.py`;

`re/out/x87/rosetta_results.json` + `rosetta_disagreements.json` (git-ignored).
